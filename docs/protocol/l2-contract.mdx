The L2 contract is where anonymous ENS ownership becomes a usable on-chain primitive. Running on Aztec, it receives the hash sent from Ethereum, waits for the user to privately supply their original inputs, and stores the resulting proof in Aztec's private state — invisible to anyone who isn't explicitly granted access. Other contracts can then read that proof to gate their own logic, without ever learning the user's Ethereum address or ENS name.

<Info>
  All state written by `claimProof` is stored in Aztec's private note tree. Neither the ENS name nor the user's L1 address appears in any public log.
</Info>

## Contract Functions

The L2 contract exposes three functions that work together in sequence.

<Steps>
  <Step title="Receive the bridged hash from L1">
    `receiveFromL1(hash)` is called automatically by the Aztec message bridge when the L1 contract's `bridgeToL2` transaction is processed. You do not call this directly — it fires as part of the cross-chain message delivery.

    ```noir
    // Called by the Aztec bridge — not by your application code
    #[aztec(public)]
    fn receive_from_l1(hash: Field) {
        // Stores the pending hash in public state
        // Marks it as unclaimed
        storage.pending_proofs.insert(hash);
    }
    ```

    Once this function executes, the hash is held in the contract, waiting for a matching claim.
  </Step>
  <Step title="Claim the proof">
    After the hash arrives, the user calls `claimProof(nameData, secret)` in a **private** Aztec transaction. The contract hashes the supplied inputs, checks the result against every pending hash from L1, and — if one matches — stores the proof privately under the caller's Aztec address.

    ```noir
    #[aztec(private)]
    fn claim_proof(name_data: NameData, secret: Field) {
        let derived_hash = pedersen_hash([
            hash(name_data),
            secret,
        ]);
    
        // Fails if no matching pending hash exists
        assert(storage.pending_proofs.contains(derived_hash));
    
        // Store proof privately; only the owner can read it
        storage.proofs.insert(
            ProofNote { owner: context.msg_sender(), name_data }
        );
    
        storage.pending_proofs.remove(derived_hash);
    }
    ```
  </Step>
  <Step title="Read the proof from another contract">
    `readProof(address, name)` lets any Aztec contract check whether a given address holds a valid NoirName proof for a specific ENS name. It also refreshes the proof's internal state if needed, so callers always work with current data.

    ```noir
    #[aztec(private)]
    fn read_proof(owner: AztecAddress, name: Field) -> bool {
        // Refresh proof state if stale
        let proof = storage.proofs.get(owner, name);
        proof.refresh_if_needed();
    
        proof.is_valid()
    }
    ```

    See the [dApp Integration](/protocol/dapp-integration) page for how to call this from your own contract.
  </Step>
</Steps>

## Public API

<CardGroup cols={2}>
  <Card title="receiveFromL1(hash)" icon="arrow-down-to-line" href="/protocol/l2-contract#public-api">
    Inbound bridge handler. Stores the arriving hash as a pending, unclaimed proof. Triggered by the Aztec message bridge — not called directly by users or dApps.

    **Params:**

    - `hash` — `Field`, the combined proof hash sent from the L1 contract
  </Card>

  <Card title="claimProof(nameData, secret)" icon="lock" href="/protocol/l2-contract#public-api">
    Private function. Hashes `nameData` and `secret`, matches the result against pending L1 hashes, and stores the proof in private state. Fails if no matching hash is found.

    **Params:**

    - `nameData` — original name inputs held by the frontend
    - `secret` — the raw secret generated by `generateSecret()`
  </Card>
</CardGroup>

<CardGroup cols={1}>
  <Card title="readProof(address, name)" icon="magnifying-glass" href="/protocol/l2-contract#public-api">
    Private read function. Returns whether `address` holds a valid proof for `name`. Refreshes stale proof state automatically so consuming contracts always read current data.

    **Params:**

    - `address` — the Aztec address to check
    - `name` — the ENS name field to match against

    **Returns:** `bool`
  </Card>
</CardGroup>

## Proof Lifecycle

<Accordion title="What does 'refresh proof state' mean in readProof?">
  ENS ownership on L1 can change at any time — a name can be transferred or expire. When `readProof` is called, the contract checks whether the stored proof is still considered current based on a configurable TTL. If the proof is stale, it flags it as needing re-verification before returning. This ensures that downstream contracts cannot rely on an outdated claim indefinitely.
</Accordion>

<Accordion title="Can a proof be claimed by someone other than the rightful owner?">
  No. The L1 contract uses `msg.sender` to verify ENS ownership, so only the address that owns the ENS name can trigger the L1 → L2 bridge transaction. On L2, `claimProof` ties the resulting proof to `context.msg_sender()` — the Aztec address that submits the claim. An attacker who somehow intercepted the hash would still need to know the original `nameData` and `secret` to produce a matching hash, which only the legitimate user holds.
</Accordion>

<Accordion title="What happens to unclaimed hashes?">
  Pending hashes remain in the contract indefinitely. If a user loses their secret before claiming, the hash is effectively inert — no one can claim it — but it does occupy storage. A future protocol version may introduce an expiry mechanism to reclaim storage from abandoned pending proofs.
</Accordion>

## Security Considerations

<Warning>
  `claimProof` must be called as a **private** Aztec transaction. Calling it as a public transaction would expose `nameData` and `secret` in the transaction payload.
</Warning>

<Note>
  The `readProof` function is also private, meaning the query itself — which address you're checking against which name — is not visible on-chain. This is intentional: consuming contracts should not leak which names they gate on.
</Note>
